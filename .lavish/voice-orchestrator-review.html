Load-bearing correction

"No Voice.app panel" isn't the same as "no Voice.app"

T1 says: replace the GUI client with "a headless Pi client on ws://127.0.0.1:8766/v1/realtime." I checked what's actually on the other end of that socket. Pi is a Node CLI agent — it has no microphone capture and no audio playback. Today, 100% of the audio I/O lives in the Swift app, not the Python server:

What this means for T1: you can't point Pi at the WebSocket and call it a headless client — Pi has no way to grab the mic or play audio back. What you actually need is a headless build of the existing Swift app: keep AudioEngine, LiveVoiceBackend, VoiceRuntime, and LocalServiceStarter exactly as they are, and delete the SwiftUI window layer (PanelController, FloatingPanel, ConversationView, SessionsView, SettingsView, OrbView, GlobalHotKey). A Pi skill launches that trimmed binary and talks to it over stdin/stdout or a small local socket — transcript out, reply text in — rather than Pi opening the realtime WebSocket itself. This is real, scoped Swift work, not a config change.

Build tasks, task by task

T1 — /voice skill boots the loop rework needed

Reads as a Pi skill launching a script and talking to a socket. It's actually: trim Voice.app to a headless binary (keep AudioEngine/LiveVoiceBackend/VoiceRuntime/LocalServiceStarter, drop the SwiftUI panel/hotkey layer), then build a small text bridge between it and Pi. That's the majority of the real effort in this whole plan, and the memo doesn't size it as Swift work.

Good news found: LocalServiceStarter.swift already does exactly "on-demand, teardown on quit" — it spawns run-browser.sh --reuse-running on launch and calls stop() on quit, with health-probe reuse logic. Answers Open Question 1 directly: reuse this, don't rebuild it.

T2 — Message pipe Pi ↔ Luna sound

Every event/class named (TranscriptionCompletedEvent, SpeechStartedEvent/StoppedEvent, SESSION_END, pipeline/control.py) exists exactly as described, timeouts included. Correctly scoped as new plumbing — nothing here can be "reused" as-is since the audio side never previously talked to an external process.

T3 — Strip Luna tools trade-off not named

The tool list is accurate. What's missing: server_tools.py's own docstring explains these tools were deliberately pulled in-process specifically to kill a round trip ("client called sidecar, posted output back, asked for a new response... none of that is necessary"). Routing them to Pi reintroduces exactly that round trip, and T3 ships before T4's async filler exists. Build the ack-filler first, or the voice will visibly get laggier before it gets smarter.

Also unaddressed: screenshot stays client-side today because macOS Screen Recording permission is granted per code identity (VoiceTools.swift + ScreenCaptureKit) — Pi's process is a different identity and won't inherit Voice.app's grant automatically. And remember/forget currently write Luna's own chat-history store — moving them to Pi means picking one of three memory stores (Luna's, Pi's own sessions, or Jack's private-journal) as the source of truth, not three.

T4 — Async, never blocks sound, but sequence-dependent

No contradicting evidence — the pipeline already has the cancellation primitives (SESSION_END, barge-in flush of both audio and LLM queues) this would hook into. Correctly placed last, but per the T3 note above, consider building its ack-filler mechanism alongside T3 rather than strictly after it.

Open questions — all decided

  • 1. Always-on vs on-demand? Decided: on-demand

    Always-on would mean the voice backend (the program listening on port 8766) starts when your Mac boots and just keeps running forever, whether or not you're using Luna — like a lamp that's always plugged in and switched on, burning power in an empty room. On-demand means it only starts the moment you actually launch Voice (or type /voice in Pi), and shuts itself down when you quit — like a lamp with a motion sensor: it lights up when you walk in, and turns off when you leave.

    Good news: LocalServiceStarter.swift already does the on-demand version today — it starts run-browser.sh --reuse-running when Voice launches and calls stop() when it quits. Nothing to build here, just carry this piece into the headless version.

  • 2. Chrome bridge Decided: retire it

    Your call — Pi doesn't need a second, separate way to read web pages. Retire web_app/chrome_article_bridge (the custom Chrome extension) and let Pi's own browser-tools skill be the one path for anything web-related.

    One thing worth a 30-second check before deleting the extension: the old bridge's whole point was reading whatever tab you already had open in your normal Chrome window, hands-free, mid-conversation. If Pi's browser-tools only knows how to open and drive its own separate browser session (rather than looking at a tab you're already on), that specific "glance at what I'm looking at" trick goes away. Not a blocker — just confirm that's an acceptable trade, or check whether browser-tools can attach to your existing Chrome window.

  • 3. Siri voice + listening language Decided: keep as-is

    As a reminder, these were two separate dials:

    • SIRI_VOICE = en-US-F — which voice Luna talks back with. "en-US" = English (United States), "F" = a female-sounding voice. This is just which Siri voice reads Pi's answers out loud.
    • STT_LOCALE = en-US — which language/accent the speech recognizer expects to hear from you. Apple's on-device engine can't auto-detect the language, so it has to be told up front: "listen for American English."

    Decision: leave both untouched for v1. Luna keeps listening for and speaking American English with the existing voice — no change needed anywhere in run-openrouter.sh.

Same word, unrelated system — no conflict with this plan, just flagging so it isn't confused with this "orchestrator" plan.

Bottom line

The architecture direction — Pi as the one brain, Luna as dumb ears+mouth, async, writer/actor split — is the right shape and matches the ChatGPT voice pattern well. The research behind it is mostly excellent (the Pi-side facts are perfect). Before building:

  1. Re-scope T1 as "headless Voice.app build," not "Pi client on the websocket" — size it as Swift work.
  2. Reuse LocalServiceStarter's existing lifecycle logic instead of rebuilding it.
  3. Decide the T3/T4 sequencing explicitly — build the ack-filler alongside the tool strip, not after.
  4. Pick one memory store before wiring remember/forget to Pi.
  5. Chrome bridge: retiring it per your call — just confirm Pi's browser-tools can read a tab you already have open, not only drive its own session, before deleting the extension.
